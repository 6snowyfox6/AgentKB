# KBRAG — все команды и настройки

Как поставить и запустить — в `ЗАПУСК.md` в корне проекта. Здесь справочник: короткие команды,
полные команды со всеми ключами и тонкие настройки.

Всё набирается в терминале, открытом в папке проекта. Короткие команды
начинаются с `python kbrag.py`, полные — с `.venv\Scripts\python -m …`:
ими пользуются, когда нужен ключ, которого нет у короткой.

---

## 1. Короткие команды

У любой команды можно сказать, с какой базой дерева работать: `--kb physics.optics`
(«.» — всё дерево). Без ключа — `база_по_умолчанию` из `config\kbs\kb.yaml`.

| Что делаем | Команда |
|---|---|
| Поднять базу | `python kbrag.py start` |
| Что работает | `python kbrag.py status` |
| Свои PDF в базу (файл или папку) | `python kbrag.py import "D:\Статьи" --kb physics.optics` |
| То же, недостающие метаданные спросить | `python kbrag.py import "D:\Статьи" --ask` |
| То же, и рисунки описывает модель со зрением | `python kbrag.py import "D:\Статьи" --figures` |
| Разобрать заново статьи базы из их PDF | `python kbrag.py reparse --kb physics.optics` |
| Разобрать заново одну статью | `python kbrag.py reparse 10.1234_abcd` |
| Загрузить разобранное в базу (import делает сам) | `python kbrag.py ingest` |
| Убрать служебный текст из уже загруженной базы (благодарности, колонтитулы, e-mail) | `python kbrag.py tidy` |
| Поискать | `python kbrag.py search "методы измерения вязкости"` |
| Спросить чат-бота | `python kbrag.py ask "как измеряют вязкость расплавов?"` |
| Подробно или кратко — словами в вопросе | `python kbrag.py ask "кратко: как измеряют вязкость?"` |
| Датасеты — у чего больше всего фактов | `python kbrag.py dataset` |
| Датасет любой сущности, таблица для Excel | `python kbrag.py dataset "метод Монте-Карло"` |
| Оценить базу и чат-бота | `python kbrag.py eval` |
| Оценить только поиск (без модели) | `python kbrag.py eval --only-search` |
| Граф: Qwen3 выписывает факты из статей | `python kbrag.py graph` |
| Проба графа на 30 фрагментах | `python kbrag.py graph --limit 30` |
| Вопросы оценки из фактов графа | `python kbrag.py questions` → `eval --questions .local/kbs/<база>/eval-graph.yaml` |
| Граф заново (после правки правил) | `python kbrag.py graph --redo` |
| Что нашла модель и где ошибалась | `python kbrag.py graph --new` |
| Перепроверить готовый граф новыми правилами кода (без модели) | `python kbrag.py graph --recheck` |
| Подтвердить факты вопросами по цитате (идёт и само после `graph`) | `python kbrag.py graph --confirm` |
| Предложения в словарь синонимов | `python kbrag.py synonyms` |
| Свести написания одного и того же (идёт и само после `graph`) | `python kbrag.py graph --names` |
| Поиск, статьи, чат-бот и граф в браузере | `python kbrag.py web` |
| То же + Телеграм-бот | `python kbrag.py web --tg` |
| Только Телеграм-бот | `python kbrag.py tg` |
| Бот молчит — проверить токен, доступ, кто писал | `python kbrag.py tg --check` |
| Сервер без браузера (только адреса /api) | `python kbrag.py serve` |
| Что в базе | `python kbrag.py stats` |
| Дерево баз: названия, сколько статей, какая по умолчанию | `python kbrag.py kb list` |
| Новая база (настройки — от ветки выше) | `python kbrag.py kb create physics.hadron --title "Адроны"` |
| Перенести базу со всем, что под ней | `python kbrag.py kb move a.b c.b` |
| Положить статьи в базу / убрать из неё | `python kbrag.py kb assign a.b ID …` / `kb unassign a.b ID …` |
| Все статьи другой базы — и в эту | `python kbrag.py kb assign a.b --from x.y` |
| Убрать базу (без `--yes` — только показать) | `python kbrag.py kb remove a.b --yes` |
| Убрать прежнюю ночную добычу из планировщика | `python kbrag.py unschedule` |
| Проверить код (без базы и модели) | `python kbrag.py test` |
| MCP-сервер для Claude Code (поверх `serve`) | `claude mcp add kbrag -- python <путь>\kbrag.py mcp` |
| Выдача, факты, ответ — одним JSON | `… search/facts/ask … --json` |
| Остановить базу | `python kbrag.py stop` |

Порядок всегда один: **импортировать → граф → искать и спрашивать.**

## 2. Импорт статей — все ключи

```
.venv\Scripts\python -m kbrag.library.cli import "D:\Статьи" --kb physics.optics --device cuda
.venv\Scripts\python -m kbrag.library.cli reparse --kb physics.optics
.venv\Scripts\python -m kbrag.library.cli reparse --doc 10.1234_abcd --doc 10.1234_efgh
```

| Ключ | Зачем |
|---|---|
| `--kb physics.optics` | в какую базу дерева положить статьи (import) или чьи статьи переразобрать (reparse) |
| `--ask` | спросить в окне название, авторов, год, журнал, DOI, если их нет ни в YAML, ни в BibTeX, ни в PDF |
| `--force` | разобрать и тот файл, что уже разбирали; заменить статью с тем же DOI другим файлом |
| `--figures` | описать рисунки моделью со зрением — фрагменты «Рисунок» (ниже, «Рисунки») |
| `--no-images` | не сохранять рисунки файлами (быстрее, места меньше) |
| `--no-ingest` | только разобрать, в базу не загружать (потом — `ingest`) |
| `--device cuda` | на чём разбирать: `cuda`, `cpu`, `auto` (короткая команда выбирает сама) |
| `--articles папка` | другая папка разобранных статей (по умолчанию `.local\acquired`) |
| `--doc ID` | reparse: только эта статья (можно несколько раз) |

Откуда метаданные: `статья.yaml` рядом с `статья.pdf` (поля `название`/`title`,
`авторы`/`authors`, `год`/`year`, `журнал`/`journal`, `doi`, `ссылка`/`url`,
`язык`/`language`), затем любой `.bib` в той же папке (запись — по полю `file`, по
ключу, равному имени файла, или по DOI), затем свойства самого PDF и DOI на первых
двух страницах. Что откуда взято — поле `meta_from` в записи статьи.

Идентификатор статьи — по DOI (как у прежней добычи: та же статья — тот же
идентификатор), без DOI — имя файла и начало отпечатка: `paper_1-ab12cd34`.
Повтор узнаётся по отпечатку файла (sha256): тот же файл не разбирается второй раз,
даже под другим именем. Если такой файл уже был в базе без PDF — путь к нему
дописывается, и статью можно переразобрать.

Что получилось — таблица в конце: «разобрана», «уже есть», «PDF привязан», «скан»,
«не разобрана», «не читается». Журнал по шагам разбора — `.local\logs`.

### Формулы

Формулы в статьях распознаются сами (в LaTeX) — модель Docling CodeFormulaV2 скачивается
при первом разборе (0,64 ГБ). Как это проверено — в `УСТРОЙСТВО.md`. Если docling
обновился и класс модели формул не найден, разбор останавливается с объяснением, а
не портит формулы молча: версии docling закреплены в `requirements.txt`.

При загрузке в базу у каждой формулы появляется запись: номер «(N)», LaTeX, текст из
PDF, страница, рамка на странице, абзацы до и после и формула словами («Формула (1):
ρ = ρ_0 (1 − φ). Плотность пород выражается через пористость. где φ — пористость»).
Во фрагменте формула стоит между `$$…$$` — страница рисует её (KaTeX), модель ответа
цитирует её дословно с номером, — а в вектор фрагмента идёт она словами, так что
вопрос «как плотность зависит от пористости» её находит. Ссылки «из формулы (55)»,
«уравнение 3», «(2)» в тексте связываются с формулой.

```
python kbrag.py formula 10.1234_abcd 55        формула (55) статьи: LaTeX, словами, кто ссылается
python kbrag.py formula 10.1234_abcd           все формулы статьи
python kbrag.py formula --find "плотность через пористость" --kb physics
```

`--json` — то же одним объектом в stdout. В Телеграме под фрагментом с формулами —
кнопки «Формула (N)»: картинка формулы (вырезка со страницы PDF; нет PDF — нарисованный
LaTeX, если стоит matplotlib) и её LaTeX. Статьи, загруженные до таблицы формул, получают
формулы при следующем `ingest` сами.

### Рисунки

Рисунки статьи сохраняются файлами всегда (без `--no-images`): папка
`.local\acquired\<doc_id>.figures`, файлы `fig-001.png`…; их перечень — номер в
статье по подписи («Рис. 3» → 3), страница, рамка, подпись, размер — в поле `figures`
записи статьи. При загрузке в базу каждый рисунок получает запись в таблице рисунков,
а ссылки на него из текста — «рис. 3», «на рисунке 2а», «(рис. 5, 6 и 7)», «Fig. 4»,
«figs. 2 and 3» — связываются с ним. Рисунок находится по смыслу — по подписи и
описанию:

```
python kbrag.py figure 10.1234_abcd 3                  «Рис. 3» статьи: файл, подпись, описание, кто ссылается
python kbrag.py figure 10.1234_abcd                    все рисунки статьи
python kbrag.py figure --find "схема установки" --kb physics
```

**Описание моделью со зрением.** Модель смотрит на сам рисунок и пишет, что на нём:
тип (карта, разрез, график, схема), район и объекты, легенду, читаемые названия и
числа. Каждый крупный рисунок становится фрагментом «Рисунок 3 (с. 9). Рис. 8. … Что
на рисунке (описание модели по изображению): …» — его находит поиск и цитирует
чат-бот («на рис. 8 [4]»). Значки, логотипы и обложка пропускаются. Слова промпта —
из настроек базы («рисунок» в `kb.yaml`).

```
python kbrag.py figures                     описать все неописанные рисунки базы --kb
python kbrag.py figures 10.1234_abcd        одной статьи
python kbrag.py figures --redo              описать заново и описанные
python kbrag.py import "D:/статьи" --figures   разобрать и сразу описать
```

Описывается по сохранённым файлам — PDF заново не разбирается; описание хранится в
записи рисунка и переживает переразбор (`reparse`). После описания статьи
загружаются в базу заново сами.

**Модель со зрением** — сервис `vision` в `docker-compose.yml`
(`Qwen/Qwen3-VL-8B-Instruct-FP8`, около 11 ГБ скачивания; другая — `KBRAG_VISION_MODEL`).
У основной Qwen3-14B зрения нет. Как они делят видеокарту — `KBRAG_VISION_MODE` в
`.local\settings.env`:

| Режим | Что делает запускатель | Когда |
|---|---|---|
| `turns` (по умолчанию) | гасит модель ответов, поднимает `vision`, описывает, гасит `vision`, поднимает модель ответов обратно; векторы — уже после, на свободной видеокарте | одна видеокарта на 16–24 ГБ |
| `shared` | обе модели работают сразу; при `import --figures` рисунки описываются по ходу разбора | 40 ГБ и больше: `KBRAG_GPU_MEMORY` и `KBRAG_VISION_GPU_MEMORY` в сумме ≤ 0,95 |
| `single` | одна модель со зрением вместо двух: сервис `llm` запускает её (`KBRAG_LLM_MODEL=Qwen/Qwen3-VL-8B-Instruct-FP8`), она и отвечает, и описывает рисунки | видеокарта одна, а останавливать чат-бот на время описания нельзя |

Чат-бот, пока в режиме `turns` описываются рисунки, не отвечает. Модель со зрением
на другой машине — `KBRAG_FIGURE_LLM` (адрес) и `KBRAG_FIGURE_MODEL` (имя):
запускатель её не трогает.

**В ответах.** Под ответом на странице — рисунки фрагментов, на которые он сослался
(стоит во фрагменте или фрагмент на него ссылается): картинка, «Рис. 3 к [2]», подпись;
нажать — целиком. В Телеграме — те же рисунки фото после ответа (до трёх), а под
фрагментом — кнопки «Рис. N».

### Язык фрагментов

У каждого фрагмента при загрузке определяется язык (`kbrag/lang.py`: по письменности
и частым служебным словам — русский, украинский, английский, немецкий, французский,
испанский, китайский, японский, корейский, арабский и другие). Не понять (таблица
чисел, формула) — язык статьи. Он хранится в базе, столбец `chunks.language`;
фрагментам, загруженным раньше, его дописывают `init` и `ingest`.

**Поиск по словам — словарём языка фрагмента.** Немецкий фрагмент стеммится
по-немецки, французский — по-французски (словари Postgres: немецкий, французский,
испанский, итальянский, португальский, нидерландский, шведский, турецкий, сербский,
греческий, хинди, арабский). Русский, английский и неизвестный — как раньше, русской
конфигурацией: она понимает оба языка. Языки без своего словаря в Postgres
(украинский, польский, чешский…) — слово как есть. Запрос строится словарями тех
языков, что есть в базе. Первый `init` после обновления перестраивает столбец поиска
по словам — на большой базе это минуты.

**Китайский, японский, корейский** — по парам знаков: слова там не разделены, и
поиск по словам Postgres их не видит. Фрагмент находится, если в нём есть хотя бы
половина пар знаков запроса.

**Чистка текста после разбора** (буквы-двойники, дефисы на концах строк) — только для
русского и английского текста: правила проверены на них. Мягкие переносы склеиваются
в любом языке.

### Сканы

Скан — PDF из картинок страниц, без текстового слоя: по умолчанию не разбирается (в
отчёте «скан»). С `--ocr` текст распознаётся с картинок:

```
python kbrag.py import "D:/сканы" --ocr
python kbrag.py reparse 10.1234_abcd --ocr       скан, импортированный раньше
```

Медленно (на процессоре — десятки секунд на страницу, на видеокарте быстрее) и с
ошибками распознавания: в записи статьи — `ocr: true`, в отчёте — «скан, текст
распознан». Ключ действует только на сканы: у статей с текстовым слоем текст берётся из
PDF, как раньше. Движок и языки — в `.local\settings.env`:

| Имя | По умолчанию | Что это |
|---|---|---|
| `KBRAG_OCR_ENGINE` | easyocr | `easyocr` (`pip install easyocr`, модели скачает сам), `tesseract` (программа tesseract с языками), `rapidocr` (`pip install rapidocr onnxruntime`) |
| `KBRAG_OCR_LANGS` | ru,en | языки сканов (коды ISO: ru, en, de, zh…); у EasyOCR китайский — только вместе с английским |

Движок не установлен — разбор останавливается с подсказкой, что поставить.

## 3. Поиск — все ключи

```
.venv\Scripts\python -m kbrag.index.cli search "вязкость расплавов при нагреве" --limit 10 --per-doc 2 --year-from 2015
```

| Ключ | Зачем |
|---|---|
| `--limit 10` | сколько результатов показать |
| `--per-doc 2` | не больше N кусков одной статьи (0 — без ограничения) |
| `--year-from 2015` | только статьи не старше указанного года |
| `--source openalex` | искать только по одному источнику |
| `--candidates 50` | сколько кандидатов брать из каждого поиска до объединения |
| `--min-similarity 0.45` | отсечь непохожее: 0.45 — обычно, 0.55 — строго, 0 — показывать всё |
| `--require-words` | только куски, где буквально есть все слова запроса |

Векторный поиск всегда возвращает ближайшее — даже когда подходящего в базе
нет. Поэтому есть порог `--min-similarity`. У BGE-M3 текст про то же самое
даёт похожесть примерно от 0.6, случайный сосед — около 0.3–0.45. Куски, где
буквально есть все слова запроса, проходят порог всегда.

У каждого результата написано, **кто его нашёл**: «вектор» — по смыслу,
«текст» — по точным словам, «оба» — согласились оба способа. «Оба» — самый
надёжный признак.

## 3а. Страница в браузере

```
python kbrag.py web
```

`http://localhost:8000`, три вкладки: **Поиск**, **Статьи**, **Чат-бот** (под
ним — граф связей). Модель векторов грузится один раз при запуске, поэтому
поиск отвечает мгновенно. Остановить — Ctrl+C в том же окне. Страница слушает
только этот компьютер: из сети к ней не подключиться.

Другой порт — `.venv\Scripts\python -m kbrag.web.server --port 9000`.
Другая модель — в `docker-compose.yml` (сервис `llm`), и то же имя — в `--model`.

### Чат-бот

Под ответом — **«Статьи, на которые опирается ответ»**: по строке на статью (авторы,
год, название, журнал), номера её фрагментов в ответе — щелчок открывает фрагмент, — и
ссылки: DOI, страница издателя, свой PDF (`/api/pdf`, открывается на первой
процитированной странице). В Телеграме — тот же список (название — ссылкой на DOI или
издателя) и кнопки «PDF 1», «PDF 2»: файл статьи сообщением (до 50 МБ). В терминале
(`ask`) — список в конце, в `ask --json` — поле `articles`.

Ниже — **«Связи из графа»**: что граф выписал из фрагментов, на которые
ссылается ответ. Щелчок по имени — оно на вкладке графа со всеми своими связями
(дальше можно ходить по соседям), по номеру [n] — сам фрагмент. В Телеграме — кнопка
«Связи» под ответом.

Как он отвечает, по шагам:

1. Qwen3 разбирает вопрос. Составной («какие признаки и какими методами их
   выделяют») делится на части, до трёх; на каждую — 3 поисковых запроса,
   по-русски и по-английски. Ищется и сам вопрос. Вопрос вдогонку
   («а при нагреве?») модель дописывает до самостоятельного — с предметом из прошлого.
2. **Поиск вместе с моделью.** Поиск приносит кандидатов с запасом (до 16 на
   вопрос, по 8 на часть составного, мягкий порог), Qwen3 **читает всех** пачками
   **и берёт только подходящие** —
   похожее по словам, но о другом, отбрасывает. Если чего-то не хватает, модель
   сама составляет новые запросы и ищет ещё — до трёх кругов. Для ответа — до 8
   фрагментов, не больше 3 из одной статьи; у каждой части вопроса свои места.
   Под ответом видно: сколько фрагментов прочла модель, сколько было кругов, чего
   не хватало и что искалось ещё. Если модель не отвечает — фрагменты берутся по
   близости, как в обычном поиске.
   - **«Что известно о …»**, «перечисли всё про …» — ответ собирается из
     датасета: фрагмент [1] — все факты о предмете вопроса из графа знаний,
     за ним — фрагменты, откуда взяты цитаты главных фактов. Предмет может быть
     любым — место, метод, процесс. Нужен построенный граф (`python kbrag.py graph`).
   - **Вопросы о самом наборе статей** — «сколько статей про …», «какие статьи
     Смита есть», «перечисли статьи 2020–2023 о …» — не по 8 фрагментам, а по всей
     базе (`chat/catalog.py`): модель при разборе даёт основы слов темы на разных
     языках, годы и фамилию автора; статья засчитывается, если тема в её названии
     или хотя бы в 2 кусках текста. Ответ собирает код — число, сколько по
     названию и сколько только по тексту, список статей со ссылками; секунды, без
     модели. Счёт по словам: статья, где тема названа иначе, не попадёт.
   - **Вопросы о связях** — «с чем связан …», «с какими
     веществами сочетается …», «что сопровождает …», «где встречается …» —
     тоже через граф: он видит все связи предмета со счётом статей, а не только
     те, что попали в 8 фрагментов. Проверка вслепую на 12 таких вопросах: через
     граф лучше в 7, поиском — в 2, вровень — в 3. Остальные вопросы идут поиском.
3. **Нашлось** — Qwen3 пишет ответ только по этим фрагментам и после каждого
   утверждения ставит номер фрагмента. Номера сверяются: ссылка на фрагмент,
   которого модели не давали, зачёркивается. Фраза без ссылки, все числа
   которой есть в одном фрагменте, получает ссылку на него; прочие фразы без
   ссылки убираются. Затем каждое утверждение сверяется с текстом своих
   фрагментов (`chat/support.py`): число не из того фрагмента — ссылка
   переставляется на фрагмент с этим числом; утверждение, которого фрагмент не
   говорит (другое место, объект, число), убирается — под ответом список
   «Утверждений, которых не подтверждают их фрагменты, убрано». Сверка — 5–20 с;
   выключить — `Settings.check_support = False`. Под ответом — источники, что
   искал бот и сколько утверждений подкреплены номером фрагмента.
4. **Не нашлось** (или модель прочла фрагменты, а ответа в них нет) — статьи
   не показываются. Бот пишет: «По вашему запросу в базе знаний такой
   информации нет» и показывает, что искал. Ответа из общих знаний модели по
   умолчанию нет: он не проверен статьями и бывает неверным. Включить его для
   базы — `общие_знания: true` в её `kb.yaml` (выключено в корневом
   `config/kbs/kb.yaml`); тогда ниже отказа модель отвечает сама, с пометкой
   «ответ модели, не из базы знаний», без ссылок на статьи.
   Если вопрос вообще не по теме базы («как испечь хлеб?») — только короткий отказ.

Размышления вслух у Qwen3 выключены — ответ в разы быстрее.

**Настроек у ответа нет.** Нужно подробно, кратко, списком, таблицей — так и
напишите в вопросе: «подробно: какие признаки…», «кратко — чем выделяют узлы?».
Не сказали — ответ по существу: вывод и главное списком.

Числа — в начале файлов `kbrag\chat\`: `settings.py` (сколько запросов и
фрагментов), `retrieval.py` (сколько кругов поиска, мягкий порог), `search.py`
(порог близости), `messages.py` (правила для модели, сколько прошлых реплик
помнить).

Из терминала — один вопрос, без разговора:

```
python kbrag.py ask "какие методы измерения вязкости описаны в статьях?"
```

## 3б. Граф знаний и словарь синонимов

### Как строится

```
python kbrag.py graph --limit 30     проба: 30 фрагментов
python kbrag.py graph                все новые фрагменты
python kbrag.py graph --redo         всё заново — после правки правил
python kbrag.py graph --new          что нашла модель и почему код отбрасывал
```

Qwen3 читает фрагменты статей и выписывает **факты**: «от — связь — к».
«метод Монте-Карло — применяется для — оценки погрешности». Предложения фрагмента
пронумерованы, и модель указывает номер предложения, где факт сказан, — цитатой
становится само это предложение. Переписывать цитату модели не нужно: ответ
вдвое короче, а цитата всегда дословная. Сущности — как их назвала статья
(место, метод, процесс — без разделения на виды), на языке статьи; связь —
по-русски, 1–4 слова. Правила для модели — `graph-rules.txt` базы (`config\kbs\<база>`, нет своего — `config\kbs\graph-rules.txt`), правятся
Блокнотом (сохранять в UTF-8); после правки — `graph --redo`.

Каждый факт **проверяет код**: в предложении должны быть видны оба конца факта
(с любыми окончаниями); если название стоит предложением выше («This area…»),
цитата — оба предложения. Не прошло — в граф не попадает. Выдуманные названия,
названия, дописанные «по смыслу», и общие имена без названия («this study»,
«predictive model», «работа [33]») так отсекаются. Затем каждый факт сразу же
**проверяется вопросами по цитате** (подробно — ниже, «Подтверждение»).
`graph --new` показывает, какие сущности и связи получились и почему код
отбрасывал остальное.

**Скорость.** У модели сразу 8 фрагментов (`--workers 8`, или переменная
`KBRAG_WORKERS`), и vLLM считает их одной пачкой. На RTX 5070 Ti выписать факты и
проверить их вопросами — 1,3 с на фрагмент (замер на 40 фрагментах, 12.10.2026);
на Ollama с 4 запросами сразу было 2,3 с, и вся база (4272 фрагмента) строилась
2 ч 44 мин (7334 подтверждённых факта, `.local/logs/graph-speed-20261010`).

**Новые статьи граф не пересчитывают.** Модель проходит только фрагменты, которых
ещё не видела, а готовый граф в памяти (страница, чат-бот, датасеты) дописывается
новыми фактами, без сборки с нуля. Всё заново — только `graph --redo` после правки
правил; с нуля собирается и граф в памяти после правки словаря синонимов.

Прервать можно в любой момент (Ctrl+C) — та же команда продолжит с того же места.
Нужна модель: `graph` поднимает её сам.

### Словарь синонимов

`config\kbs\<база>\synonyms.yaml` — разные написания одного и того же сводятся к одному
имени:

```
имена:
  метод Монте-Карло: [Monte Carlo method, метод МК, MC simulation]
связи:
  приурочено к: [приурочен к, associated with]
```

Первое — как показывать, в скобках — как ещё пишут. Падеж и число не важны:
«Донецкого бассейна» узнаётся само. Чего в словаре нет, в граф идёт как написала
модель. Сюда — только настоящие синонимы (перевод, сокращение, другое
написание); «random forest» и «машинное обучение» — не синонимы, это факт.

Правка действует **сразу**: модель заново проходить не нужно, страницу — просто
обновить, бота перезапускать не надо.

Пополнять словарь помогает модель:

```
python kbrag.py synonyms
```

Она находит похожие имена (векторы BGE-M3) и по парам решает, одно ли это.
Предложения — в `.local\kbs\<база>\synonyms-предложения.yaml`, в том же виде, что словарь.
Откройте Блокнотом, нужные строки перенесите в `synonyms.yaml`, ошибочные — просто
не переносите. Сама модель словарь не правит. Строже или мягче —
`.venv\Scripts\python -m kbrag.graph.cli synonyms --threshold 0.85` (обычно 0.8;
выше — меньше предложений).

### Автосинонимы: одно и то же, записанное чуть иначе

```
python kbrag.py graph --names          новые имена графа — к уже известным
python kbrag.py graph --names --redo   все имена заново (после правки правил)
```

Модель пишет одно и то же по-разному: «Landsat8 OLI» и «Landsat-8 OLI»,
«mineralised zones» и «mineralized zones», «рудопроявление Эльвенейское» и
«Эльвенейское рудопроявление». Это сводится **само**, без словаря: имя каждой
сущности графа превращается в вектор, новое имя сравнивается с пятью ближайшими
уже известными (через индекс, не со всеми), и при похожести от 0,95 становится
их написанием. Идёт само после `graph` и проходит только новые имена — 9439 имён
с нуля считаются около 80 с.

Слить похожее, но разное не дают правила кода: разные числа («JCBN50» и
«JCBN45»), стороны и степени («Восточное» и «Западное рудное тело», «high thorium
and low uranium» и «high uranium and low thorium»), разные собственные имена.
Проверено 11.10.2026: из 74 слитых пар ошибочных нет, правила остановили 18.

Переводы и сокращения («золото» — «gold», «PCA») так не сводятся: у них похожесть
векторов в среднем 0,70 — для них остаётся словарь, и **словарь главнее**: имя из
`synonyms.yaml` автосинонимы не трогают. Похожие от 0,85 до 0,95 сами не
сливаются — там одно и то же лишь в половине пар; их предлагает `synonyms`.
Что слито, видно в таблице `entity_names` (колонка `canon` — чьё это написание).

### Датасеты

```
python kbrag.py dataset                     у чего больше всего фактов
python kbrag.py dataset "метод Монте-Карло"    все факты о нём, файл CSV для Excel
```

Датасет есть у любой сущности: все факты о ней — с чем и как связана, в скольких
статьях, цитата и статья. Факты о том, что в неё **входит** (по фактам «входит
в»), тоже попадают: датасет щита включает его зоны. Таблица кладётся в
`.local\datasets`. То же — в карточке узла на графе и в Телеграме (/dataset).

Готовых датасетов нет: каждый собирается из фактов в момент, когда его
открывают. Новый `graph` — новые сущности и их датасеты появляются сами.

### Граф на странице

Под чат-ботом — все факты одной сетью, как граф в Obsidian: сущности (синие) и
статьи (серые). Стрелка — факт, по направлению связи; тонкая линия — от статьи к
сущностям, о которых в ней факты. Колесо — масштаб, тянуть фон — сдвиг. Щелчок
по сущности — её датасет: строки фактов, нажатие на строку — цитата и кнопка
статьи; «Спросить чат-бота» — вопрос «что известно о …». Щелчок по статье — о
чём в ней факты и «Разбор статьи целиком».

### Адреса

Сервер — тот же, что открывает `python kbrag.py web` (`serve` — без браузера).

| Адрес | Что отдаёт |
|---|---|
| `GET /api/network` | сеть: сущности, статьи, факты с цитатами |
| `GET /api/datasets` | у каких сущностей больше всего фактов |
| `GET /api/dataset?name=метод Монте-Карло` | датасет сущности; `&format=csv` — таблицей; POST — то же JSON в теле |
| `GET /api/kbs` | дерево баз, выбранная база, её название и примеры вопросов |
| `GET /api/search?q=…` | фрагменты; `limit`, `per_doc`, `year_from`, `min_similarity`, `require_words=1` |
| `GET /api/fragment?chunk_id=5` | фрагмент целиком |
| `GET /api/article?doc_id=…` | статья: метаданные, ветки, рисунки, число формул; `&text=1` — и фрагменты, страницей: `offset`, `limit` (20, до 50), в ответе `fragments_total`, `next_offset` |
| `GET /api/formula?doc_id=…` | формулы статьи с теми, кто на них ссылается; `&number=55` — одна, «(55)» |
| `GET /api/formulas?q=…` | формулы по смыслу (по описанию), `kb`, `limit` |
| `GET /api/formula_image?id=…` | формула картинкой: вырезка со страницы PDF или нарисованный LaTeX |
| `GET /api/pdf?doc_id=…` | свой PDF статьи (`#page=N` — на странице N); права — по статье |
| `GET /api/figure?doc_id=…&n=1` | рисунок файлом (или `?id=…` — по таблице рисунков); без `n` — перечень рисунков с теми, кто на них ссылается, `&label=3` — «Рис. 3» |
| `GET /api/figures?q=…` | рисунки по смыслу (подпись и описание), `kb`, `limit` |
| `POST /api/chat` | ответ чат-бота потоком: `{question, history, kb, conflicts, fast}` |

У любого адреса — `kb=путь` (`.` — всё дерево): по какой базе отвечать.

С другой машины — `python kbrag.py web --remote` (ниже, «Удалённо: Tailscale») или
SSH-туннель.

## 3б-2. Доступ к базам по людям

```
python kbrag.py access add ИМЯ --kb ВЕТКА [--kb ВЕТКА…] [--telegram ID] [--no-token]
python kbrag.py access list
python kbrag.py access remove ИМЯ [--kb ВЕТКА]
python kbrag.py access token ИМЯ          новый токен (старый перестаёт работать)
python kbrag.py access guests [--kb ВЕТКА] что видит гость открытого бота
```

Файл `.local\access.yaml` (`kbrag/acl.py`):

```yaml
люди:
  Анна:
    базы: [physics.optics, chemistry]   # ветка — со всем, что под ней; «.» — всё
    telegram: 123456789
    токен_sha256: 5e88…                  # отпечаток токена входа
гости: []                                 # гость открытого бота
```

| Где | Без `access.yaml` | С `access.yaml` |
|---|---|---|
| Страница, `/api/*` | всем, кто открыл | только по токену (`?token=` один раз → cookie; заголовок `X-KBRAG-Token`); иначе 401 |
| Выбор базы | любая | только свои ветки, их части и то, что над ними; чужая — 403 |
| Статья, фрагмент, формула, рисунок по id | видны | чужие — 404, как будто их нет |
| Телеграм | `telegram_users.txt` | ещё и люди из файла — по своим веткам; владельцы из `telegram_users.txt` — всё |
| Гость открытого бота («*») | всё | ветки из `гости` |
| MCP | всё | по `KBRAG_TOKEN` |
| Команды в терминале | всё | всё |

Файл с ошибкой — страница не пускает никого, пока его не поправят (лучше никого, чем
всех). Правка действует сразу, перезапуск не нужен.

## 3в. Claude Code: MCP и вывод в JSON

### MCP-сервер

Claude Code (и любой клиент MCP) может искать по базе знаний сам. MCP-сервер работает
поверх запущенного сервера страницы и ходит в его адреса `/api` — модели векторов и
реранкера уже загружены там, поэтому сам он лёгкий и стартует сразу.

```
python kbrag.py serve                                         в своём окне, не закрывать
claude mcp add kbrag -- python D:\projects\AgentBK\kbrag.py mcp     один раз
```

Дальше в Claude Code: «найди в базе знаний, как измеряют вязкость» — он вызовет
инструменты сам. Сервер на другом адресе — переменная `KBRAG_SERVE` (по умолчанию
`http://127.0.0.1:8000`): `claude mcp add kbrag -e KBRAG_SERVE=http://сервер:8000 -- …`.

| Инструмент | Что делает |
|---|---|
| `list_kbs` | дерево баз: путь (параметр `kb` у остальных), название, сколько статей |
| `search(query, kb, limit, per_doc)` | фрагменты по смыслу и словам в базе `kb` и под ней («.» — всё дерево); у каждого `chunk_id`, `doc_id`, статья, страницы, текст |
| `get_fragment(chunk_id)` | фрагмент целиком |
| `get_article(doc_id, text, offset, limit)` | статья: метаданные, в каких базах лежит, рисунки, сколько формул; `text` — текст по фрагментам, страницей (`next_offset` — следующая) |
| `facts(name, kb)` | факты графа о сущности с цитатами; без `name` — у чего фактов больше всего |
| `get_formula(doc_id, number)` | формулы статьи: LaTeX, номер «(N)», страница, текст из PDF, абзацы до и после, какие фрагменты на неё ссылаются |
| `search_formulas(query, kb)` | формулы по смыслу — по их описанию словами |
| `get_figure(doc_id, n)` | рисунок картинкой и его подпись |
| `search_figures(query, kb)` | рисунки по смыслу — по подписи и описанию |

### Удалённо: Tailscale

С другого компьютера — страница в браузере и Claude Code. На удалённой машине нужен
только Tailscale (частная сеть между своими устройствами: трафик зашифрован, порты в
интернет не открываются) и Claude Code; проект туда не ставится.

Один раз на этой машине:

1. Tailscale: tailscale.com/download, войти. На удалённой машине — то же, тем же
   аккаунтом (или пригласить человека в свою сеть Tailscale).
2. Люди с токенами: `python kbrag.py access add Анна --kb physics.hadron.elsm` — печатает
   токен. Как только появился `.local\access.yaml`, страница и MCP пускают **только** по
   токену — и на этой машине тоже (себе — `access add Я --kb .`).

Запуск:

```
python kbrag.py web --remote          или serve --remote — без браузера
```

Страница слушает 127.0.0.1 и адрес Tailscale (100.x.y.z), MCP по HTTP — тот же адрес,
порт 8200; в локальную сеть и интернет — ничего. Адреса и команда для Claude Code
печатаются при запуске. Без людей с токенами `--remote` не запускается. Свой VPN вместо
Tailscale — адрес в `KBRAG_REMOTE_HOST` (`.local\settings.env`).

На удалённой машине:

```
http://ИМЯ-МАШИНЫ:8000/?token=ТОКЕН        страница (токен — один раз, браузер запомнит)
claude mcp add --transport http kbrag http://ИМЯ-МАШИНЫ:8200/mcp --header "Authorization: Bearer ТОКЕН"
```

Каждый запрос MCP идёт к странице с токеном того, кто спросил: человек видит только
свои базы. Отобрать доступ — `access remove ИМЯ` или `access token ИМЯ` (новый токен),
действует сразу. Только MCP, без страницы для других: `python kbrag.py mcp --http --host
100.x.y.z` (рядом с запущенным `serve`).

Сервер страницы не запущен — инструмент отвечает ошибкой с подсказкой, что запустить.
Формулы — из таблицы формул базы (у статей, разобранных запасным парсером, формул нет:
у него нет разметки), рисунки — из файлов, сохранённых при импорте; у статей прежней
добычи рисунков нет, пока их не переразобрать (`reparse`).

### Вывод в JSON

Для скриптов и для Claude Code без MCP — ключ `--json`: в stdout — один объект JSON,
всё остальное (что делается, сообщения запускателя и Docker) — в stderr.

```
python kbrag.py search "методы измерения вязкости" --json
python kbrag.py facts "метод Монте-Карло" --json
python kbrag.py ask "как измеряют вязкость расплавов?" --json --kb physics.optics
```

`search` — `{query, kb, hits: [{chunk_id, doc_id, title, year, pages, text, score, …}]}`;
`facts` — датасет сущности (или список сущностей без названия); `ask` — `{answer,
sources, used, mode, coverage, search, timings, …}`: текст ответа уже без фраз без
ссылки на фрагмент (убранные — в `removed`).

## 4. База в Docker

```
docker compose up -d          # поднять (первый раз — создаёт)
docker compose stop           # остановить, данные остаются
docker compose ps             # что сейчас работает
docker compose logs db        # что пишет база, если не поднимается
```

**Никогда:** `docker compose down -v` — удаляет том с базой, и всё придётся
загружать заново.

Перезагрузить всё в базу с нуля, не трогая разобранные статьи:

```
python kbrag.py ingest --force
```

Граф при этом сохраняется: фрагменты узнаются по тексту, даже если номера сдвинулись
(новый абзац, другая нарезка); факты стираются только у фрагментов, чей текст
поменялся, и следующий `python kbrag.py graph` пройдёт их заново.

## 5. Языковая модель (vLLM)

Языковая модель — Qwen3-14B, сжатая до 4 бит (`Qwen/Qwen3-14B-AWQ`), в **vLLM** — в
Docker рядом с базой. Она пишет ответы чат-бота, выписывает факты графа
(`graph`, `synonyms`) и отбирает статьи. Векторы считаются без неё (BGE-M3 в самом
приложении).

```
python kbrag.py start        поднять базу и модель (в первый раз скачает ≈ 19 ГБ)
python kbrag.py status       что работает и отвечает ли модель
python kbrag.py stop         остановить базу и модель — видеокарта свободна
docker logs kbrag-llm        журнал модели: почему не поднялась
docker stop kbrag-llm        остановить только модель (база работает)
```

`web`, `ask`, `graph`, `eval` поднимают модель сами, если она не запущена. Модель
грузится 1–2 минуты (первый запуск — дольше: vLLM собирает свои ядра под видеокарту);
поиск в это время уже работает.

Настройки — в `docker-compose.yml`, сервис `llm`: модель, окно (`--max-model-len`,
то же число, что `NUM_CTX` в `kbrag/llm.py`), доля видеопамяти
(`--gpu-memory-utilization`). Числа берутся из `.local\settings.env` (ниже, «Настройки
машины»), а без него — для 16 ГБ. Имя модели для проекта — `qwen3-14b`
(`--served-model-name`). Адрес — переменная `KBRAG_LLM` (по умолчанию
`http://localhost:8100`; на 8000 — веб-страница): если модель работает на сервере,
задайте его, например `setx KBRAG_LLM http://сервер:8100`. Говорит проект с моделью по протоколу OpenAI
(`/v1/chat/completions`), так что сервер можно сменить (llama.cpp, SGLang), не
трогая код.

### Настройки машины (`.local\settings.env`)

Один файл на машину, в git не идёт; по строке `ИМЯ=значение`, `#` — комментарий.
Его читает программа (`kbrag/machine.py`) и `docker compose` (`python kbrag.py
start` передаёт его ключом `--env-file`). Переменная окружения с тем же именем
главнее файла.

| Имя | По умолчанию | Что это |
|---|---|---|
| `KBRAG_NUM_CTX` | 12288 | окно модели вместе с ответом, токенов (`--max-model-len`) |
| `KBRAG_TOP_K` | 8 | сколько фрагментов чат-бот даёт модели для ответа |
| `KBRAG_PER_DOC` | 3 | из них — не больше стольких из одной статьи |
| `KBRAG_GPU_MEMORY` | 0.90 | доля видеопамяти для vLLM |
| `KBRAG_LLM_MODEL` | Qwen/Qwen3-14B-AWQ | модель ответов в сервисе `llm` |
| `KBRAG_VISION_MODE` | turns | как модель со зрением делит видеокарту: `turns`, `shared`, `single` (§2, «Рисунки») |
| `KBRAG_VISION_MODEL` | Qwen/Qwen3-VL-8B-Instruct-FP8 | модель со зрением в сервисе `vision` |
| `KBRAG_VISION_GPU_MEMORY` | 0.90 | доля видеопамяти для неё |
| `KBRAG_VISION_CTX` | 8192 | её окно, токенов |
| `KBRAG_MAX_SEQS` | 8 | сколько запросов vLLM считает одной пачкой |
| `KBRAG_BATCHED_TOKENS` | 2048 | сколько токенов задания vLLM читает за шаг |
| `KBRAG_TOKEN` | — | токен человека для MCP (`access add`), если доступ ограничен |
| `KBRAG_TG_GUEST_LIMIT` | 20 | вопросов в час гостю открытого бота («*»); 0 — без ограничения |
| `KBRAG_DB_POOL` | 10 | соединений с базой в пуле на процесс; 1 — без пула |
| `KBRAG_EXACT_MAX` | 50000 | ветка (или чужой узкий доступ, год, источник) не больше стольких фрагментов ищется перебором — точно и быстро; больше — векторным индексом; 0 — всегда индексом |
| `KBRAG_RERANKER` | BAAI/bge-reranker-v2-m3 | реранкер; `off` — отбирает модель, как раньше |
| `KBRAG_RERANK_DEVICE` | auto | где считать реранкер: `cuda`, `cpu`; auto — видеокарта, если на ней есть место рядом с vLLM |

Окно и число фрагментов связаны: восемь фрагментов с соседними кусками — около 7
тысяч токенов. С окном 32 768 можно давать 16–20; что не влезет, программа сама
отбросит с конца (`fit_budget`). После правки окна — `stop` и `start`: сервер модели
берёт его при запуске.

### Резюме статей и поиск сверху вниз

При загрузке статьи (`import`, `ingest`) модель пишет резюме каждого раздела (3–5
предложений: объекты, методы, данные, выводы) и по ним — резюме всей статьи. Модель
не запущена — загрузка идёт без резюме, а дописывает их потом:

```
python kbrag.py summaries                  резюме, которых нет (база --kb)
python kbrag.py summaries --redo           все заново
python kbrag.py summaries 10.1234_abcd --show    показать резюме статьи
```

`--no-summaries` у `import` и `ingest` — без резюме. Изменился текст раздела
(переразбор) — его резюме пишется заново, остальные остаются.

Чат-бот ищет **сверху вниз**: статьи — по резюме статей, в них — разделы по резюме
разделов, и среди фрагментов этих статей — обычный поиск, фрагменты найденных
разделов первыми. Это ещё один набор кандидатов рядом с поиском по всей базе: в
большой базе он держит в фокусе статьи, которые про вопрос целиком.

**Обзорный вопрос** («обзор методов…», «какие работы есть о…», «что известно о … в
целом») отвечается по резюме статей: источник «Резюме статьи» на каждую из
подходящих статей (до восьми) вместо восьми кусков из двух-трёх статей. Числа и
подробности модель берёт из фрагментов текста, резюме — для обзора.

### Реранкер и быстрый режим

Кандидатов для ответа отбирает **реранкер** bge-reranker-v2-m3 (`kbrag/index/rerank.py`):
читает пару «вопрос — фрагмент» и даёт число от 0 до 1, подходит — от 0,2. Раньше их
читала Qwen3, пачками по 12, по нескольку секунд на пачку. Теперь Qwen3 зовётся,
только если подходящего мало (на часть вопроса — меньше двух, на простой вопрос —
меньше трёх): одним вызовом говорит, чего не хватает, и даёт запросы, а новых
кандидатов снова оценивает реранкер. Без видеокарты рядом с vLLM реранкер считается на
процессоре — медленнее (несколько секунд на вопрос); сколько он занял, видно в «Как
искал» («отбор») и в `.local\logs\chat-<дата>.log`. Выключить — `KBRAG_RERANKER=off`.

**Быстрый режим** — галочка на странице, `/fast` в Телеграме: вопрос не разбирается
моделью (ищется сам вопрос — векторы BGE-M3 находят и статьи на других языках),
модель не участвует в отборе, сверки статей нет. Модель зовётся один раз — написать
ответ.

### Несколько пользователей и видеокарта на 16 ГБ

vLLM сам собирает одновременные запросы в одну пачку. Страница и Телеграм-бот
стоят в одной очереди (`kbrag/turns.py`): до 2 ответов сразу (переменная
`KBRAG_PARALLEL` в `.local\settings.env`), остальные ждут и видят своё место — «вы в
очереди, перед вами N». Граф — 8 фрагментов сразу. Сверх того каждый запрос к модели
берёт место в бюджете памяти vLLM под задания (`kbrag/llm.py`, `Budget`): объём сервер
узнаёт у vLLM (`/metrics`), задать вручную — `KBRAG_KV_TOKENS`. Без этого два человека
сразу (а ответ — ещё и несколько запросов параллельно: разбор, отбор, сверка)
переполняли память, vLLM вытеснял запросы, и они падали по таймауту у обоих. Бюджет —
на процесс: `graph` или `summaries` в другом окне одновременно со страницей его не
делят. Замер 12.10.2026, RTX 5070 Ti 16 ГБ:

- модель занимает 9,4 ГБ, служебная память vLLM — около 2 ГБ, под окна остаётся
  13 600 токенов (окна — в 8 битах, `--kv-cache-dtype fp8`). Это одно полное окно
  или 2–3 обычных задания чат-бота (5–7 тыс. токенов);
- рядом свободно около 3 ГБ — модели векторов этого мало: вместе с ней память
  кончалась, Windows гоняла её через общую, и vLLM писал 20–35 токенов в секунду
  вместо 76. Поэтому, пока работает vLLM, векторы сами считаются на процессоре:
  вопрос — 60 мс вместо 25, это незаметно. Загрузка статей на процессоре медленная
  (2,4 фрагмента в секунду вместо 190) — большую загрузку делайте при остановленной
  модели: `docker stop kbrag-llm`, `python kbrag.py ingest`, `docker start kbrag-llm`;
- один запрос: читает 2680 токенов в секунду, пишет 76 — как Ollama (3000–3400 и
  72). Одинаковое начало заданий не перечитывается (кэш начала);
- граф: 1,3 с на фрагмент при 8 сразу против 2,3 с на Ollama;
- чат-бот, один пользователь, 29 вопросов оценки: медиана 25,8 с, 95 % — до 35,6 с
  (на Ollama 25,4 и 34,6 с);
- чат-бот, несколько человек сразу (каждый ждёт свой ответ):

| сколько спрашивают | vLLM | Ollama (11.10.2026) |
|---|---|---|
| один | 27 с | 24 с |
| двое | 34 и 40 с | 36 и 47 с (2 слота — 36 и 37 с) |
| четверо | 37, 41, 44 и 49 с | 4 слота не помещались — 143 с |

**На сервере выигрыш больше**: там под окна десятки гигабайт — на одной карте 48 ГБ
(L40S) около 30 одновременных заданий, по оценке 340–840 вопросов в час; на 80 ГБ
(A100) — 590–950 (оценки, мерить на месте). На сервере уберите из
`docker-compose.yml` строки `--max-num-seqs` и `--max-num-batched-tokens` (они
ужимают vLLM под 16 ГБ); модель векторов там поместится на той же карте.

На 16 ГБ без `--max-num-seqs=8 --max-num-batched-tokens=2048` vLLM не запускается:
служебная память под сотни запросов сразу съедает всё место под окна («No available
memory for the cache blocks»).

### Оценка базы и чат-бота

```
python kbrag.py eval                  поиск и ответы по вопросам базы (eval-questions.yaml в её папке)
python kbrag.py eval --only-search    только поиск — если модель не работает
python kbrag.py eval --only s01,t01   отдельные вопросы
python kbrag.py eval --no-graph       то же без графа: сравнить с обычным прогоном, что граф даёт ответам
```

Отчёт — `.local\logs\eval-<дата>.md` (открывается Блокнотом) и `.json`. В начале отчёта
итог и сравнение с прошлым прогоном, дальше таблица по вопросам и разбор того,
что не прошло: не нашлось, нет ключевого, короткий ответ, мало ссылок, ответил
по базе на вопрос не по теме. Раздел «Где базе не хватает статей» — по каким понятиям
добавить статьи (`import`). Вопросы — свои у каждой базы: ближайший к ней
`eval-questions.yaml` по дереву (`--kb`).

Свои вопросы — в `config\kbs\<база>\eval-questions.yaml`; формат описан в начале
образца `config\kbs\geology\ore\anabar\eval-questions.yaml`. Лучше всего работают вопросы, ответ на которые вы сами знаете по статьям.
